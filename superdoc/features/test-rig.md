# Local test rig (known talkers on demand)

A script-driven, fully loopback setup for proving per-speaker audio processing: a local TeamSpeak server, two isolated
"talker" clients whose microphones are PipeWire virtual sources fed with generated test WAVs, and one isolated modded
"listener" client whose playback is a null sink that tests record. Code: `tools/rig/` (`rig`, `make-wavs.sh`, `js.mjs`).

Related: [agc.md](agc.md) (the native module the listener preloads, control API),
[ts6-modding-surface.md](ts6-modding-surface.md) (CDP, page globals, talk-status events, Vue state).

## Why (decision D13)

- The real server's bots are silent, and per-speaker work needs **known talkers on demand** (bursty speech, quiet speech,
  start-of-speech peaks) that can be repeated bit-for-bit.
- Keeping everything on loopback and in throw-away profiles leaves the real server, real client and real profile untouched.
- The listener carries the real native module (`native/libts6mod.so`) so a hook can be checked end to end: talker mic ->
  server -> listener decode/mix -> `pa_stream_write` -> null sink -> recording.

## Requirements

`ffmpeg`, `bc`, `curl`, `ss`, `pactl`, `pw-play`, `pw-record` (PipeWire with the Pulse layer), Node >= 22, `ccorral`,
a C compiler (the listener builds `native/libts6mod.so` via `make -C native` if missing), the client at
`/opt/teamspeak/TeamSpeak` (override `TS6MOD_TS_BIN`). The server is downloaded once: `tools/rig/rig fetch-server`
(official TeamSpeak 3 server 3.13.8, linux amd64, from the vendor's release host, into `$HOME/tmp/ts6-rig/server/`).
Everything else lives under `$HOME/tmp/ts6-rig` (override `RIG_DIR`); nothing goes into the repo or `/tmp` (tmpfs).

## Commands

```
tools/rig/rig up                      # sinks + server + listener + talkers; idempotent; waits until all three clients see each other
tools/rig/rig check                   # smoke test: each talker plays a WAV, recording + talk status checked, ids printed
tools/rig/rig status                  # what runs, client ids as each client sees them, the mod's GET /status
tools/rig/rig talk <A|B> <wav|name>   # play a WAV into that talker's mic; blocks until finished (name: bursty, quiet, tone)
tools/rig/rig record <sec> <out.wav>  # record what the listener plays (48 kHz mono s16)
tools/rig/rig down                    # stop clients and server, unload the null sinks; nothing is left running
tools/rig/rig wavs | fetch-server     # (re)generate the WAVs / download the server
node tools/rig/js.mjs <cdp-port> '<expr>' | @file.js    # evaluate JS in that client's UI page, print JSON
```

All long-running processes are started with `ccorral -- ...`. PIDs of the clients and server are written to
`$HOME/tmp/ts6-rig/run/*.pid`; `down` also kills by CDP port / profile path, so a stale pid file cannot leave anything behind.
Server credentials (serveradmin password, API key, privilege token) land in `$HOME/tmp/ts6-rig/creds.env`.

## Ports and names

| What | Where |
|---|---|
| Server voice | UDP `127.0.0.1:9989` |
| Server query (raw) / filetransfer | TCP `127.0.0.1:10111` / `127.0.0.1:30034` (non-default, SSH query off) |
| Listener (`RigListener`) | CDP `9230`, mod control API `127.0.0.1:39001` (`TS6MOD_PORT`) |
| `RigTalkerA` / `RigTalkerB` | CDP `9231` / `9232` |
| Talker mics | PipeWire null sinks `ts6rig_talk1` (A), `ts6rig_talk2` (B); the client captures the `.monitor` source |
| Listener output | null sink `ts6rig_out`; record from it |
| Other sinks | `ts6rig_deaf` (talkers' playback, so nobody blasts the speakers), `ts6rig_idle` (listener's silent "mic") |

Do not use 9222 / 38998 (the normal client and its control API). Each client also tries the Remote Apps websocket port
5899 and logs `bind() failed: Address already in use` once a client holds it; harmless.

## Layout (`$HOME/tmp/ts6-rig`)

```
server/teamspeak3-server_linux_amd64/   unpacked server (downloaded)
server/data/                            database + logs, recreated on every cold start of the server
profiles/<listener|talkerA|talkerB>/    home/ config/ cache/ data/ state/ tmp/  = HOME and XDG_*_HOME of that client
  client.log                            stdout/stderr of the client
  config/ts6-mods/agc.json              listener only: the module's own config (separate from a real profile)
  state/ts6-mods/ts6mod.log             listener only: module log
wav/{bursty,quiet,tone}.wav             generated by tools/rig/make-wavs.sh
run/*.pid, creds.env, check/*.wav       pids, credentials, recordings of the last `rig check`
```

## How it works

- **Server** (`rig:srv_up`): `ts3server` with `TS3SERVER_LICENSE=accept`, `voice_ip`/`query_ip`/`filetransfer_ip` = 127.0.0.1.
  Fresh database per cold start. No permission tweaks were needed: the default channel needs no talk power and guests
  talk (own talk power read as 0 and speech arrived).
- **Profiles** (`rig:client_env`): `HOME`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `TMPDIR`
  all under the profile dir; `PULSE_SOURCE` picks the mic and `PULSE_SINK` the playback device (the client honours both).
- **First-run wizard and connecting** (`rig:client_up`): every fresh profile opens a first-launch wizard (splash, Terms 1-4, a
  TeamSpeak account sign-in step that cannot be passed without an account) that blocks all connecting. It is shown while the
  UI model `appController.showFirstStart` is true (`!welcomeDisplayed`), so `up` sets `appController.welcomeDisplayed = true`
  over CDP (the wizard disappears, nothing is accepted or created). It then connects with `appController.openConnection(<plain
  ConnectInfo object>)` + `showItem(...)`, the same call the UI's quick-connect search uses; the identity is created
  automatically. A `ts3server://` URL argument is **not** used: it only works as a hand-off to an already running instance
  of the same profile and is silently dropped while the wizard is up.
- **Talkers** (`rig:talker_setup`): capture preprocessor `vad`, `denoise`, `agc`, `typing_suppression` set to `false` over the
  bridge (`setPreProcessorConfigValue`, see ts6-modding-surface.md). Push-to-talk is off by default, so with VAD off the
  client transmits continuously (silence included).
- **Listener**: `LD_PRELOAD=native/libts6mod.so`, `TS6MOD_PORT=39001`; its own `XDG_CONFIG_HOME` keeps the module disabled
  (no config = vanilla) until a test posts `POST /config`. It captures from the silent `ts6rig_idle` source.
- **Test WAVs** (`tools/rig/make-wavs.sh`, ffmpeg `aevalsrc`, 48 kHz mono s16, 12 s): `bursty.wav` = 0.9 s "words" every
  1.5 s with 4.5 Hz syllable modulation and a 15 ms onset spike at every word start (peak about -0.2 dBFS, body peaks about
  -15 dBFS, whole-file RMS about -26 dBFS); `quiet.wav` = the same body, whole-file RMS -35 dBFS; `tone.wav` = 1 kHz at
  -20 dBFS, 8 s.
- **Ids**: `rig check` prints the clientIds of `RigTalkerA/B` as the listener sees them (UI model
  `serverConnectionHandler.GetFlatListClients()`), ids are assigned in connect order and are **not stable across runs**; map by
  nickname each time.

## Record and measure

```
tools/rig/rig talk A bursty & tools/rig/rig record 14 out.wav; wait      # start recording a second before the talker plays
ffmpeg -hide_banner -nostats -i out.wav -af volumedetect -f null -        # mean_volume (RMS), max_volume (peak)
ffmpeg -hide_banner -nostats -i out.wav -af astats=metadata=0 -f null -  # per-channel peak / RMS / crest factor
```

Compare with the source (`ffmpeg -i $HOME/tmp/ts6-rig/wav/bursty.wav -af volumedetect ...`): the codec path costs a little
level, the listener's own mixing none. Toggle the module with `curl -s -X POST 127.0.0.1:39001/config -d '{"enabled":true}'`
(the `Origin`/`Host` rules in [agc.md](agc.md) allow plain curl on loopback) and compare recordings of the same WAV.

The listener keeps the client's **stock playback AGC on** (the default, like a real client), which changes levels: in a
test `quiet.wav` (RMS -35, peak -21 dBFS) was recorded at RMS -27 / peak -10 dBFS with it on and at -36 / -20 dBFS with it
off. For a transparent baseline start with `RIG_STOCK_AGC=off tools/rig/rig up` (or call
`setPlaybackConfigValue(schid, 'agc', 'false')` over CDP, see ts6-modding-surface.md).

## Add a talker

Add a null sink name to `SINKS` and a line to `CLIENTS` in `tools/rig/rig` (`name cdp-port nickname mic-source playback-sink`,
e.g. `talkerC 9233 RigTalkerC ts6rig_talk3.monitor ts6rig_deaf`); `EXPECT` follows the array length; extend the
`A|B` case in `cmd_talk` and the pairs in `cmd_check`.

## Known limits and gotchas

- **Fresh profile on every start** (`rig:client_up`, skip with `RIG_KEEP_PROFILES=1`): a reused profile comes back with a
  "Confirm your Account" login wall and the connection activity stays without a `serverConnectionHandler`. That is why we wipe
  instead of reusing. Consequence: identities, clientIds and the listener's `agc.json` are new each `up`.
- **Talk status is not informative**: with VAD off both talkers show `flagTalking` permanently, so it cannot tell who is
  speaking at a given moment. Separate talkers by playing one at a time, or by content.
- Use `pw-play --target` and `pw-record --target <sink> -P stream.capture.sink=true`. `paplay -d <sink>` and `parecord
  -d <sink>.monitor` produced digital silence on this PipeWire setup.
- The UI page pumps native events only while visible; the clients open real windows on the desktop.
- Never launch `ts3server://` URLs by hand next to a real client: a URL launch with no running instance of that profile exits
  at once and may be handed to a differently-profiled running TeamSpeak.
- Do not `Page.reload` a rig client (see ts6-modding-surface.md); restart it with `rig down` / `rig up`.
- The rig does not inject the Mods panel; it launches the binary directly with the preload (the panel/launcher are not needed
  to test the audio hook).
- The client process ends with a segmentation fault when `rig down` sends SIGTERM (seen on all three instances, also without the
  preload, so not the module); harmless, but it leaves a core-dump notice if the system collects them.
- `rig up` from cold takes about a minute; `rig check` about 35 s. Client ids are the same (3 and 4) on every cold start in
  practice because the server database is recreated, but do not rely on it.
- **Stray clients**: a `ts3server://` URL launched with the rig's profile env while no instance of that profile runs is not
  handled by a new process; during development such launches reached a *different*, already running client (the normal
  one), which then kept a connection tab to the rig server and re-connected every time the server came up (it showed up in
  the server's client list under the URL's nickname). `rig up` therefore kicks every client whose nickname is not
  `RigListener`/`RigTalkerA`/`RigTalkerB` (`rig:kick_strays`) and logs it; if that happens, close the stale connection tab
  in the normal client.
